### 3. 现有能力，避免把“部分已有”误写成缺失

Reverie 已有项目分组、会话新建/重命名/归档/分叉/回退/删除/全文搜索、草稿恢复、模型及提供商选择、思考等级、实时工具活动、批准面板、Context Engine 文件和符号 `@` 推荐、任意文件选择器、图片/视频输入路径、图片生成模型、MCP/本地插件/技能、SubAgents、RATS/RTP、工作区索引、回滚检查点、深浅主题及背景。Python 侧也有 Git 历史、blame、提交详情和未提交状态检索。证据见 [桌面 README](../ReverieCli-ui/README.md)、[工具清单](../ReverieCli-py/reverie/agent/tool_manifest.json)、[Git 检索](../ReverieCli-py/reverie/context_engine/git_integration.py) 和 [安全边界](SECURITY_PERMISSIONS.md)。

因此，下文的 Git 审查、终端、工作树等项目多数是**缺少用户可直接操作的完整界面或隔离模型**，不是说 AI 无法通过已有工具读取 Git 或执行某个命令。对媒体输入也要区分“提供商和核心可以识别图片”与“桌面输入器对图片提供完整的拖放、粘贴、缩略图和发送前检查”。

### 4. 逐项差距

<a id="codex-gap-analysis-2026-09-29--a-输入栏附件与消息控制"></a>

#### A. 输入栏、附件与消息控制

| ID / 优先级 | Codex 参照及 Reverie 现状 | 具体差距与建议验收 |
| --- | --- | --- |
| A01 / P0 | Codex 桌面端可把图像加入对话；Web/CLI/IDE 也各有粘贴、拖放或图像参数路径 [C4]。Reverie 此次增加磁盘文件拖放，已有回形针。 | **剪贴板截图 `Ctrl+V`** 未在桌面输入栏处理：`Composer` 有 `onDrop`，没有 `onPaste`。应支持粘贴 PNG/JPEG、显示待发送预览、删除和多张顺序；检查只含图像而无文字的发送是否可用。当前复制文件路径不等于实现截图粘贴。 |
| A02 / P0 | Codex 有直接附加图像的输入路径 [C4]；Reverie 附件芯片仅有文件图标、名称和大小。 | 对照视觉附件任务所需的发送前检查，图片拖入后应显示缩略图、宽高/格式、可放大预览和移除；视频应至少显示类型、时长或首帧，让用户能发现拿错图或顺序错。 |
| A03 / P1 | Codex 可用 `@` 引用工作区文件 [C3]；Reverie 用 Context Engine 推荐 `@` 文件/符号，附件被复制并插入 `@` 路径。 | 对常规仓库文件缺少明确的“原位引用还是复制附件”选择；复制会制造另一份快照，原文件再修改时容易与引用版本不一致。建议仓库内文件优先原位引用，仓库外文件复制并标明来源和副本位置。 |
| A04 / P1 | Codex 的输入与文件工作流可针对多种文件提供上下文 [C3][C4]。Reverie 拖放上限 20 个，`Promise.all` 全部复制。 | 超过上限、文件过大、网络盘断开或其中一个文件失败时没有逐文件进度、失败清单和可重试动作；部分已复制文件可能残留。应有总量/单文件限制、批次结果、取消和部分成功的清理策略。 |
| A05 / P1 | Codex 在不同表面支持图像/文件附加 [C4]。Reverie 拖放仅通过 `File` 实际磁盘路径处理。 | 文件夹拖入没有递归列表、忽略规则、总文件数和确认预览；从网页或剪贴板拖来的无磁盘路径对象会被过滤。应分别给出“暂不支持”的明确反馈，并在未来设计目录导入。 |
| A06 / P1 | Codex 桌面端运行中可选择 **Steer** 当前运行或 **Queue** 下一轮，队列可编辑、重排、立即发送、删除 [C3]。Reverie 运行中按 Enter 会硬中断内核并发送新提示。 | 缺少两种行为的显式选择；硬中断会丢失未持久化的部分输出。应把“补充当前任务”“排队下一轮”“停止并改问”区分，并在提交前说明影响；队列显示在输入框上方，支持编辑/取消。 |
| A07 / P1 | Codex 可以在长运行任务中接收后续约束 [C3][C5]。Reverie 只有停/继续和上述硬中断路径。 | 模型正等待工具、审批或长命令时，用户不能把补充信息无损并入正在运行的上下文。需要后端 turn 级消息队列或安全中断点，不应只改按钮文案。 |
| A08 / P2 | Codex 支持输入器中明确的文件引用与命令提示 [C3]。Reverie `@` 弹层可选，回形针与 `/skill`、`/compact` 也有入口。 | `@` 搜索结果目前偏推荐排序，缺少最近文件/完整路径/文件类型可见过滤；文件名相同的结果难快速区分。建议键盘上下选择、路径高亮和“只看当前目录”等轻量筛选。 |
| A09 / P2 | Codex 输入器通常可把附件和消息作为一个可审阅单元 [C4]。Reverie 附件芯片与 `@` 文本是两个同步状态。 | 用户手动删除 `@` 文本后芯片仍可能存在，直接粘贴同一路径也不会生成芯片；移除芯片只替换首次出现的引用。应让附件成为结构化草稿，序列化发送时统一生成引用，避免状态不同步。 |
| A10 / P2 | Codex 的输入/长任务表面能明确提示任务运行状态 [C3][C5]。Reverie 有实时活动和任务条。 | 输入框没有“待发送文件正在复制”“当前消息将中断任务”等持续状态，错误只以短暂 toast 反馈。应提供可见的传输状态、失败操作和稳定错误摘要。 |

<a id="codex-gap-analysis-2026-09-29--b-git代码审查与发布"></a>

#### B. Git、代码审查与发布

| ID / 优先级 | Codex 参照及 Reverie 现状 | 具体差距与建议验收 |
| --- | --- | --- |
| B01 / P0 | Codex 审查面板可看未提交、暂存、提交、分支和最近一轮差异 [C1]。Reverie 的 `FileChanges` 只显示**当前运行中由文件编辑工具记录**的会话改动。 | 缺少完整仓库视图：手改文件、外部工具改动、暂存区、新文件、删除和 Git 外文件都应有一致入口；需要清楚标注比较基准，并与“本轮 AI 变更”并列。 |

| B03 / P0 | Codex 审查面板支持提交并推送 PR 分支 [C1]。Reverie 有 Git 检索及被审计的命令执行，但无桌面 Git 发布流程。 | 缺少差异检查、选择暂存文件、编辑提交说明、提交、推送、远端/目标分支校验及失败恢复。AI 可以调用命令不构成用户可核对的出版流程。 |
| B04 / P1 | Codex 支持在 PR 上看上下文、评论与文件差异，并让代理修复选定评论 [C1]。Reverie 未见 GitHub/GitLab PR 面板或评论模型。 | 需要 PR 关联、鉴权、评论定位、审查状态、选中评论形成任务、提交后回看 diff；首次版本至少只读 PR + 本地改动映射。GitHub/GitLab 可按连接能力分别提供。 |
| B05 / P1 | Codex 有逐行/逐文件审查反馈路径 [C1]。Reverie 差异用 `<pre>` 展示，无行号、内联评论或定位到代理。 | 应支持新旧行号、折叠上下文、选中行创建反馈、回跳文件路径、评论状态；注释须绑定文件和版本，避免代码变化后指向错误行。 |
| B06 / P1 | Codex 可选 branch/commit 作为比较基准 [C1]。Reverie 此次只显示和切换分支。 | 分支弹层缺少 ahead/behind、upstream、最后提交、远端新旧状态；不能在不切换工作树的情况下比较分支。先做只读元数据和比较，再考虑合并/变基。 |

| B09 / P1 | Codex 与 GitHub 等连接配合，PR/分支可形成可审阅成果 [C1][C9]。Reverie 没有原生 PR 创建/更新及 CI 状态汇总。 | 建议在推送后展示 PR 标题/正文草案、目标分支、检查状态、审查反馈和打开链接；身份与权限依赖连接，不能只用模型生成 URL 代替。 |
| B10 / P2 | Codex 审查页针对 Git 状态组织差异 [C1]。Reverie 的会话差异是截断文本，二进制/大文件只给“不可用”。 | 需要大 diff 分页、文件树、搜索、文件类型预览、二进制摘要、重命名/移动识别、空白字符和换行差异选项；至少让用户知道被截断的文件和原始文件可打开位置。 |
| B11 / P2 | Codex 的 Git 视图能在操作后持续反映工作树状态 [C1]。Reverie 本次状态在项目切换、聚焦或打开弹层时刷新。 | 外部终端改分支/新提交时若窗口持续聚焦不会立刻刷新；需文件系统或轻量轮询监听 `.git` 与工作树并防抖，切换时保留搜索/焦点。 |
| B12 / P1 | Codex `/review` 有未提交改动、基准分支、指定提交等审查范围，并把发现定位到差异 [C1]。Reverie 首页“审查变更”只是填入自然语言提示。 | 缺少确定的 diff 基准、专用审查运行类型、只读约束、发现优先级与位置存储。应让用户在开始前选审查范围，审查结果可逐条打开对应行，并能与普通聊天继续讨论。 |
| B13 / P2 | Codex 本地项目可包含多个 Git 仓库，审查页提供仓库选择器 [C1]。Reverie 的工作区 Git 栏只针对当前项目目录归属的一个仓库。 | monorepo 中嵌套仓库、子模块或多目录项目无法在统一审查页切换；先检测仓库边界，再以只读列表明确每个仓库的根与状态，避免把父库分支误标给子库。 |

#### C. 并行工作、环境、终端和自动化

| ID / 优先级 | Codex 参照及 Reverie 现状 | 具体差距与建议验收 |

<a id="reverie-cli-feature-additions-2026-09-30--1-产品定位与取舍原则"></a>

### 1. 产品定位与取舍原则

Reverie 的主要价值是：在用户本机、当前项目与实际 Git 仓库中，使用不同模型及现有 Context Engine、技能、插件、SubAgents、RATS/RTP 完成可验证的编码任务。优先补齐用户高频经过的路径：**附加上下文 → 执行和追加要求 → 查看产物 → 检查变更 → 运行验证 → 提交结果**。

| 判断因素 | 本文的决定 |
| --- | --- |
| 高频操作是否受阻 | 截图粘贴、纯附件消息、运行中追加消息、完整 diff、终端、打开生成文件直接进入默认范围。 |
| 是否已有基础能力 | 优先给现有模型、Git、命令执行、草稿、审批、技能和恢复能力补用户界面及明确协议，避免做第二套相同系统。 |
| 是否影响用户判断 | 所有执行动作都显示真实项目、会话、分支、运行状态与结果；用户要能看见实际发送的附件和实际提交的变更。 |
| 是否需要新平台 | 远程设备、托管云、同步账号与大型连接市场暂缓；单机产品不因此被扩展为一整套云平台。 |
| 是否可缩小而保留价值 | 先做只读文件预览、轻量目标、单仓库 Git 闭环；复杂编辑器、无限自主目标和完整 Git 客户端不进入默认范围。 |
| 是否能取得验证证据 | 涉及文件、Git、进程的能力必须走真实磁盘、真实仓库和打包版；有凭据限制的服务单列缺证，不用模拟结果代替。 |

Codex 用作交互参照。Reverie 沿用自己的名称、图标资源、模型体系与扩展能力，采用简洁的聊天、输入器和工作面板层级。**不增加 Local/Cloud 切换。**后面的本地 worktree 用“独立工作目录”表达，始终在本机执行。

#### 3.2 视觉与窗口适配

- 沿用项目的 CSS tokens、Lucide 图标、Reverie 标识、深浅主题、背景及现有字号/消息宽度偏好。中性表面和细边框承载层级；品牌色用于选中、焦点和主操作，避免所有卡片同时高亮。
- 间距采用现有尺度统一到 4/8/12/16/24 px 等级。对话正文、次级元数据、代码字体分别有清楚层级；路径可复制并展开，避免只剩重名文件的短名称。
- 图标按钮至少提供约 32×32 px 点击区域、可见焦点与中文/英文可访问名称。重要动作给文字说明；危险动作的颜色不能成为唯一提示。
- 在 1440×900、1280×800、1024×768、800×600 的逻辑视口分别检查。宽窗口允许聊天与工作面板并排；中等窗口先收起侧栏；窄窗口将工作面板作为可关闭的覆盖视图，保留输入器、发送和停止。分支菜单和对话框不超出可视区域。
- 125%/150% 系统缩放、长中文、长路径、大字号都要可用；每个区域独立滚动，弹层、附件条与终端不能盖住发送按钮。禁止通过全局缩小字号“解决”拥挤。

<a id="reverie-cli-feature-additions-2026-09-30--33-状态键盘与反馈"></a>

#### 3.3 状态、键盘与反馈

- 需要区分空白、加载、成功、部分成功、失败、过期、取消、等待审批和能力不可用。错误放在所属面板并提供下一步，toast 只用于补充反馈。错误出现后用户要能找回它。
- 状态必须来自后端事件；未知总量显示不定进度，不能用定时动画伪造百分比。长操作显示实际阶段和可取消条件。
- 输入器支持中文输入法组合态、Enter 发送、Shift+Enter 换行；运行中默认 Enter 排队。Steer 采用明确选择，并显示当前快捷键；快捷键不覆盖终端、`@` 列表或对话框已有含义。
- `@`、分支列表、命令目录、附件和队列支持键盘操作。Escape 关闭当前最上层可关闭浮层并把焦点交回触发控件；打开面板不抢走正在输入的草稿焦点。
- 阅读历史时流式输出不拉回底部，显示“回到最新”及新内容提示；切换面板/过滤不重置阅读位置。复制操作有反馈；提交表单失败时保留用户输入。
- 可访问名称、状态文字和 aria-live 使用真实语义。对比度目标为正文 4.5:1、较大文字/关键边界 3:1；实际测量后再声明达到目标。支持 reduced motion。全程只用键盘完成主要路径。

### 4. 默认功能逐项规格

#### S01 — 统一桌面外壳、消息层级与操作反馈（R1）

**决定：完善。**新增功能会增加控件，先确定共同布局才能避免把首页、聊天、设置和 inspector 拼成多套风格。

- **行为与入口：**按第 3 节组织会话栏、输入器、按需工作面板和 Git 栏。保留会话名称、用户自定义显示名称、模式/模型能力及偏好；名称仍只影响用户消息的展示。
- **UI/UX：**用户消息、模型回复、工具活动、最终结果各有稳定层级；工具输出默认以状态/摘要显示，详情按偏好展开。空会话给少量可理解的启动动作；“审查变更”直接进入 S11 的范围选择，不能只是填一句自然语言。

- **验收：**在四种视口、两种主题、中文与英文、大字号下完成新建会话、输入、打开变更/文件、返回聊天和保存名称；过程中草稿及滚动位置正确，发送/停止始终可见。对关键状态保存实际运行截图。

<a id="reverie-cli-feature-additions-2026-09-30--s02--工作区会话归属与结构化草稿保存r1"></a>

#### S02 — 工作区/会话归属与结构化草稿保存（R1）

**决定：完善，作为其他功能前提。**附件、队列、异步结果须和已有文本草稿使用同样清楚的归属。

- **行为：**草稿包含文本、附件/引用元数据、顺序和导入状态；按规范化项目根 + 会话 ID 保存。新会话有独立临时草稿，创建正式会话时迁移一次。旧版文本草稿可读取，不丢失原输入。
- **UI/UX：**顶部可检查当前项目和会话；切换时明确加载状态。保存失败显示“草稿未保存”和可操作原因；恢复时文件已不存在的附件显示失效卡，可重新选择或移除。
- **归属约束：**异步导入、索引、Git 查询、模型请求、预览及审批绑定发起时的工作区/会话/请求版本。切到 B 后，A 的完成事件不得把结果塞进 B；有必要时更新 A 的草稿/记录。S20 引入执行器后继续沿用这些身份。
- **验收：**两个项目可以有相同会话 ID；分别编辑文本和附件、切换、重启后恢复正确。慢速导入和 Git 请求期间切项目，结果只更新原归属；强制退出后恢复最近已落盘的文本及附件元数据。故意制造保存失败，界面不能假报已保存。

<a id="reverie-cli-feature-additions-2026-09-30--s03--截图粘贴结构化附件预览与纯附件发送r1"></a>

#### S03 — 截图粘贴、结构化附件、预览与纯附件发送（R1）

**决定：新增并完善，是最高频缺口之一。**附件成为一份可检查的数据，不再靠芯片和手写 `@` 文本维持两套状态。

- **入口：**回形针、输入器磁盘文件拖放、`Ctrl+V` 粘贴 PNG/JPEG 截图共用导入路径。纯文本粘贴仍插入光标处；附件也能在模型回复期间加入下一条草稿。支持仅有可发送附件而无正文的消息。
- **引用规则：**工作区内文件默认原位引用，卡片标“工作区引用”；外部磁盘文件和剪贴板图片存入项目 `.reverie/attachments`，卡片标“附件副本”。用户可显式把工作区文件固定为副本；普通引用在实际发送时读取当前内容，副本保持导入版本。待发送卡片和已发送记录区分，记录本轮真正使用的路径/版本信息。
- **UI/UX：**图片显示缩略图、格式、宽高、大小，点击放大；普通文件显示名称、完整路径/来源和大小。支持移除、键盘重排与拖拽重排；卡片顺序即模型收到的顺序。移除草稿卡片不删除原始文件，也不删除历史消息依赖的副本。
- **导入状态：**每文件显示等待/复制/就绪/失败/取消；失败可重试或移除，成功项保留。默认每消息最多 20 个附件，单文件 50 MiB、总量 200 MiB；提供商存在更小已知限制时显示有效限制。限制为这一版的固定规则，不新增大量设置项。准备未完成或失败未处理时阻止发送并指出对应文件。
- **边界：**文件夹递归导入和网页无磁盘路径拖入暂缓；明确显示不支持，并引导用 `@` 选工作区文件。剪贴板图像是明确支持的独立路径，不能因为没有磁盘路径而被过滤。副本只清理确认无人引用的失败临时文件，不自动清理整个附件目录。
- **内核接入：**发送前统一序列化附件/引用，复用已有媒体解析与提供商能力；不在正文维护同一附件的第二份表示。图片理解能力未知或不支持时，持久提示切换模型/移除附件，不静默降级成路径文字。不得把“成功复制文件”当成“模型收到并理解图片”。
- **验收：**真实 Windows 剪贴板截图、两个磁盘图片、一个文本文件进入同一草稿，预览/删除/重排后实际输入只含剩余条目。纯图发送走打包版到支持图片的真实模型；没有相应凭据时保留该项缺证。另验部分复制失败、超量/超限、文件消失、运行中追加、切换和重启；前一轮结束不得清空下一轮草稿。

#### S05 — Queue / Steer / Stop 与消息队列（R1）

**决定：新增完整语义。**当前 `interruptAndSend` 会取消并重启核心；需要从协议实现正确行为。Codex 的 Steer/Queue 区分是交互参照，Reverie 必须实现自身真实生命周期。[官方 Prompting](https://learn.chatgpt.com/docs/prompting#steering-and-queuing)

| 动作 | 预期行为 | 界面反馈 |
| --- | --- | --- |
| 空闲时发送 | 发起一轮新执行 | 本条从草稿转入消息；只清空已发送草稿。 |
| 排队 Queue（运行时默认） | 保存下一轮消息，当前轮结束后按序执行 | 输入器上方队列卡；可编辑、重排、删除，显示附件和目标会话。 |
| 补充当前任务 Steer | 把约束递交当前运行的安全接收点，不杀进程 | 显示“等待接收”→“当前运行已接收”；不把仅在前端存着的消息标成生效。 |
| 停止 Stop | 协作取消当前运行/受其管理的命令并保存记录 | 显示“正在停止”→“已停止”；说明外部进程是否仍运行。 |

- **入口与键盘：**运行中以两项并排切换选择“排队下一轮”或“补充当前任务”，使用 Reverie 主题样式，停止独立。选择项支持箭头键及 Home/End；Enter 按当前行为发送、Shift+Enter 换行，Steer 快捷键可发现；输入法组合态不发送或切换选择。切换 Queue/Steer 不丢草稿。
- **协议与顺序：**队列条目有稳定身份、会话/工作区及生命周期；文字、顺序和附件副本在排队时固定，工作区引用在出队前重新核对并按实际执行时内容读取。引用丢失或能力变化时暂停该条并显示原因，文件版本更新须在条目/执行记录中可检查。每会话一次只运行一轮；失败/停止后队列暂停，用户可继续，避免在异常上下文里自动执行后续项。审批等待时仍可补充或编辑下一轮；补充消息不会被当成批准。
- **可接收时机：**在工具之间、模型请求前或支持的流式控制点接收。长命令不可安全改变时显示等待原因；不谎称命令已经遵从新要求。强制停止仅在协作取消失败时成为明确的后备动作，并保留最后可持久化状态。
- **验收：**真实长命令运行中排队两条，重排/删除后只执行正确的一条；Steer 生效期间核心 PID 不变，已有输出保存。停止只影响目标运行，记录完成、未完成与未知副作用；重启后恢复队列为待确认状态，不能重复自动发送。

#### S07 — 完整仓库 diff 与大型变更浏览（R2）

**决定：新增并完善。**现有 `FileChanges` 的会话编辑工具记录保留为独立范围；增加从真实 Git 读取的工作区/index/提交视图。Codex 的仓库差异范围为参照。[官方 Code review](https://learn.chatgpt.com/docs/code-review#what-changes-it-shows)

- **范围与数据：**工作树未暂存、已暂存、指定提交、相对基准分支、本轮 AI 变更。基准分支对比分别标明 merge-base 与目标提交；不能把两分支 tip 的简单差异冒充 merge-base 审查。显示新建、删除、修改、重命名、二进制和冲突状态；覆盖用户与外部工具的改动。

- **大变更：**按文件懒加载，长 diff 分块；截断/不可显示文件给真实原因及打开原文件入口。二进制给大小/类型摘要；支持忽略空白的只读查看选项。增删行统计不得把截断预览计为完整总量。

- **验收：**临时仓库包含手改、AI 编辑、staged+unstaged 同文件、新文件、删除、重命名、二进制、冲突和大量文件；各范围与 Git 命令结果一致。读取期间切项目不串结果；大 diff 不一次渲染全部文件，输入器可继续响应。

#### S08 — 文件/hunk 暂存、取消暂存与撤销（R2）

**决定：新增，必须与 diff 一起交付。**优先支持文件和 hunk，整范围暂存/取消暂存通过可核对清单实现。

- **动作：**对当前快照的文件/hunk 执行暂存、取消暂存；“暂存所选/全部”显示实际文件范围。二进制、新增/删除和不能分 hunk 的内容明确只支持文件级操作。冲突文件引导到现有编辑器处理，解决前禁用不适用操作。
- **撤销定义：**撤销未暂存片段只改变目标工作树片段、保留 index。撤销已暂存内容必须解释是否先取消暂存和影响哪些片段；不借用含混的“恢复”按钮处理多种 Git 状态。未跟踪文件的删除是单独危险动作，不能被“撤销全部”顺手删除。
- **UI/UX：**动作贴近文件/hunk；危险动作预览具体路径和范围并由用户确认。默认无盲目的全工作区 reset/clean；若提供批量撤销，必须显式选择文件并逐项核对。成功后原位置刷新并给可追溯结果，不将所有文件折叠。
- **并发与版本：**动作携带读取时的版本信息，执行前重读确认；文件已改变则提示刷新，禁止把旧 patch 强套到新内容。Git index 锁、同一 checkout 的代理写入和外部修改都需真实处理；不能用前端按钮 disabled 代替后端校验。
- **验收：**同一文件有两个未暂存 hunk 和一个已暂存 hunk；仅暂存其中一个，再取消暂存/撤销指定 hunk，其余内容和用户旧改动完全保持。重复点击、CRLF、空格路径、二进制、index 锁、快照过期都有正确结果；不出现隐式 stash/reset/clean。

<a id="reverie-cli-feature-additions-2026-09-30--s09--提交与普通推送闭环r2"></a>

#### S09 — 提交与普通推送闭环（R2）

**决定：新增本地 Git 发布流程。**不依赖仓库托管商；PR 创建属于 T01。

- **提交：**明确展示当前仓库/分支、完整 index 清单、diff 和提交说明。提交只作用于当前 index，不能替用户把全部工作树自动暂存。原先已暂存的用户内容也必须出现在清单；不想提交的内容引导取消暂存后再提交。AI 可生成说明草稿，用户可编辑。
- **推送：**显示可选 remote、目标 ref、upstream 和将推送的提交。提交与推送是独立动作；普通 push 失败显示认证、保护分支或非快进原因及下一步。第一版不提供 force push 或静默 pull/rebase。无 remote 时给配置入口/说明，不假设一定名为 `origin` 或托管在 GitHub。
- **UI/UX：**“提交”“推送”表单保持路径/分支可见；提交 hook 运行和网络操作有阶段状态；失败保留说明及暂存内容。成功卡显示真实提交 SHA、remote/ref 与已推送结果，能回看对应 diff；不能用生成的链接充当服务成功证据。
- **确认语义：**用户点击具名动作即执行该动作，不再叠加无意义二次确认。只有不可逆丢弃、已知高风险或后端明确要求批准时增加对应确认。默认流程不自动提交/推送代理生成的内容。
- **验收：**真实临时 bare remote 上完成部分暂存→提交→推送；工作树未选改动保留，remote ref 与本地提交 SHA 相同。另验无 upstream、无 remote、非快进、hook 失败和认证失败；界面不得误报成功。

<a id="reverie-cli-feature-additions-2026-09-30--s10--分支元数据安全切换与实时刷新r2"></a>

#### S10 — 分支元数据、安全切换与实时刷新（R2）

**决定：完善已有截图式分支控件。**任何 Git 仓库都适用，托管商不会决定能否显示分支。

- **弹层：**保持主区域底部向上展开、搜索在顶、local/remote 分组、当前项勾选、新建在底。显示 upstream、ahead/behind、最后提交摘要；远端列表注明来自本地 refs，“刷新远端”由用户显式触发 fetch。没有 fetch 的数据不能称为最新远端状态。
- **切换预检：**列出未提交/冲突状态、目标分支及可能受影响内容，给“查看变更/取消”的路径。无冲突的正常切换无需每次强迫确认；Git 拒绝时在弹层持续显示错误和处理方式。分支在其他 worktree 使用时显示占用目录，不诱导强制切换。
- **上下文：**代理、action 或目标 checkout 的活动进程可能与切换冲突时阻止操作并显示具体任务；成功后刷新索引、Git 数据和会话的目录/分支提示。打开的预览标记版本已变化。Detached HEAD 显示提交缩写并提供创建分支入口。
- **刷新：**处理 `.git` 目录或 worktree 的 `.git` 文件形式；监听/轮询使用实际 git-dir/common-dir 和工作树，不只写死 `.git/refs`。窗口聚焦、显式操作及外部修改后更新，并保留搜索、焦点和选中项。
- **验收：**本地/远端独有分支、多个 remote、符号 HEAD、dirty/conflict、detached、分支已被 worktree 占用、无 Git 可执行文件与普通目录都可正确呈现。用外部终端修改 branch/index，当前窗口能更新；切项目时旧状态不闪回。

#### S11 — 行级反馈与专用只读代码审查（R2）

**决定：新增。**“审查”必须有稳定范围、定位与结果格式；普通聊天里一句“检查一下”仍可使用，但不算这个原生流程。

- **入口：**输入 `/review` 或首页/变更面板的“审查”动作，选择未提交、基准分支或指定提交，显示实际范围和额外审查要求。运行结果进入当前会话，能在工作面板按文件/优先级查看。
- **只读约束：**专用运行类型只能使用已核对的读取能力；禁止文件修改、提交、push 和任意可写 shell/插件。不能只靠提示词“请勿修改”；记录型元数据可写应用自身存储，不修改被审查的代码。这里的工具限制不等于 OS 沙箱。
- **意见：**每条包含优先级、触发条件、实际/预期行为、证据、文件/行范围及审查时版本。点击回到 diff；文件后来改动时标“基于旧版本”并需重定位。用户可给行/区域写本地反馈并加入下一条草稿，形成可核对的修复任务；提交反馈不自动启动写入。
- **UI/UX：**审查卡显示范围、进度、失败/取消和是否有发现；“未发现问题”必须区别于“审查失败”。保留本地已查看/已处理状态并按版本失效；不自动把 AI 发现标成已验证缺陷。选择“修复这些意见”才进入普通写入工作流。
- **验收：**已知缺陷的临时仓库可得到对应行意见，并回跳正确版本；运行过程中尝试写文件的能力被后端拒绝。完成前后代码/index SHA 不变；重复审查和文件版本变化不会把旧意见错贴到新行。

<a id="reverie-cli-feature-additions-2026-09-30--s12--本地文件定位与基础产物预览r2"></a>

#### S12 — 本地文件定位与基础产物预览（R2）

**决定：新增基础预览，复用系统编辑器。**避免让“生成了文件”成为用户无法检查的结果。

- **入口：**聊天中的本地文件/行链接、附件卡、diff 文件名、产物卡统一打开右侧“文件”。支持工作区路径与 Windows 空格/中文路径，`path:line` 不和驱动器冒号混淆；网页仍使用浏览器。外部文件仅在用户选择/明确授权的来源范围内访问，不根据模型生成路径任意读盘。
- **首批格式：**只读代码/文本（行号、搜索、跳行、复制）、Markdown 渲染/源码、图片（适合窗口/缩放/尺寸）、PDF（页码/翻页）与隔离的静态 HTML。其他文件给格式和系统打开/复制路径，不假装预览已成功。S03 附件预览复用同一基础能力。
- **UI/UX：**产物卡显示名称、类型、来源轮次、版本/更新时间、打开与复制路径；用户输入附件和代理产物有不同来源标签。多个文件可切换，返回同一文件时记住位置。两个关联截图可前后切换，不新增专业图像编辑器。
- **边界：**HTML 预览无 Node/Electron bridge 和本机任意读写能力，默认禁止脚本/外部网络；外链与下载走明确入口。文件过大、缺失、已修改、解码失败都有可操作状态；允许在用户指定系统编辑器中打开定位。
- **验收：**真实生成代码、Markdown、PNG、PDF、HTML 后从聊天打开并回到原位置；验证中文/空格路径与行号。包含脚本/外链的 HTML 不获得应用权限；项目切换不显示旧文件。未支持格式显示降级入口。

<a id="reverie-cli-feature-additions-2026-09-30--s13--按会话绑定的用户终端r3"></a>

#### S13 — 按会话绑定的用户终端（R3）

**决定：新增真实 PTY。**现有 AI `execute_command` 工具继续存在；用户需要在聊天旁直接验证和观察持续进程。

- **行为：**底部终端绑定项目、会话和实际工作目录，支持交互输入、窗口尺寸变化、复制/粘贴、搜索、退出码、多个终端页及显式结束进程。切到其他会话不杀掉原终端；返回原会话找回其会话和输出。
- **UI/UX：**终端标题显示路径、shell 与运行/退出状态；用户终端和代理命令标明执行主体。右键菜单/键盘提供复制选中输出、清屏、搜索、结束和“附加到草稿”；长日志可截取有行范围的片段。
- **代理读取：**只有当前归属且允许读取的终端输出提供给代理，显示来源；不自动上传所有其他会话历史。回传日志先进入草稿供检查；环境变量秘密值不通过诊断数据自动回传。
- **生命周期：**Windows 用真实支持的 PTY 路径，其他平台清楚报告支持状态。会话归档/项目关闭/应用退出时显示仍运行终端并按明确操作处理；不能只留下孤儿服务。停止代理不能无故结束用户手工开的终端。
- **验收：**在打包版跑实际交互命令、测试失败命令和持续服务；验证输入、中文输出、尺寸、退出码、Ctrl+C、切会话保留、回传选中日志及应用退出清理。只把已有命令输出放进 `<pre>` 不算完成。

<a id="reverie-cli-feature-additions-2026-09-30--s14--项目-action-与显式环境初始化r3"></a>

#### S14 — 项目 action 与显式环境初始化（R3）

**决定：新增最小项目配置。**让用户能反复执行测试、构建、启动，而不用重新描述命令。

- **配置：**复用可用项目设置存储，记录 action 名称、命令、相对工作目录和必要环境变量引用；提供测试/构建/开发服务器的可编辑条目。环境初始化与普通 action 分开，用户明确触发。打开陌生项目不自动执行仓库内脚本。
- **UI/UX：**会话运行菜单显示项目 action，编辑页可检查命令和目录，执行后打开绑定终端。每项显示真实未运行/运行中/成功/失败、时间和结果入口；失败日志可加入下一条消息。
- **环境规则：**敏感值不写进可提交配置，使用既有本机秘密/环境来源并显示变量名。初始化不能自动覆盖用户环境；重复执行由用户决定，已运行进程可停止/重开。worktree 创建后的初始化步骤显示在其创建进度中。
- **验收：**创建并执行真实 test/build/dev action，验证正确目录和退出码；重启后配置保持，失败条目可回传日志。未授权初始化不运行；工作目录含中文/空格及缺少依赖时有清楚错误。

<a id="reverie-cli-feature-additions-2026-09-30--s15--审批范围与真实能力边界展示r1"></a>

#### S15 — 审批范围与真实能力边界展示（R1）

**决定：完善现有审批，提前交付。**不以一张新卡片宣称新增了 OS 沙箱。

- **卡片：**展示动作、实际命令/参数、工作目录、已知目标路径、连接/网络需求、风险来源、批准作用域和对应会话/运行。不能确定的副作用写“未知/工具声明”，不写“仅修改这些文件”等未经强制约束的保证。
- **动作：**拒绝、批准本次与后端确实支持的扩大作用域分开；不存在的授权级别不展示。输入补充要求不会自动成为批准。审批过期、已处理或所属任务停止时卡片失效，重复点击不重复执行。
- **UI/UX：**当前会话内持续可见，后台会话在侧栏/通知标“需审批”，点击定位原任务。权限概要提供实际生效范围；Default/Auto Check/Strict 等原有模式保留清楚解释。软件工具限制、模型提供商传输与 OS 隔离分开说明。
- **核心证据：**当前安全文档明确该系统是能力隔离与工作区结果恢复，非 OS sandbox。界面按真实边界展示；OS 隔离另见 T05。[本项目安全说明](SECURITY_PERMISSIONS.md)
- **验收：**真实受控动作在批准前不执行；批准仅覆盖显示作用域，拒绝/取消正确返回。切项目或并行运行不误批别的任务；停任务后的卡片不能执行。未知网络/路径范围正确标注，不伪造安全保证。

<a id="reverie-cli-feature-additions-2026-09-30--s16--每轮执行记录与保守恢复r3"></a>

#### S16 — 每轮执行记录与保守恢复（R3）

**决定：完善既有会话/恢复能力。**保存足够的执行事实，让用户知道能从哪里继续。

- **记录：**以运行 ID 关联用户输入/附件、模型、目录/分支、工具开始/结束、审批、文件差异、测试命令/退出码和最终输出。沿用已有事件与存储，补缺少的身份、持久化和关联；不为此重写成独立审计平台。
- **UI/UX：**“运行”视图按轮显示摘要和时间线，能打开命令日志、diff、产物及批准记录。结果卡区别“代码已实现”“验证通过”“仍缺证据”；失败和取消保持可回看。导出可读 Markdown 摘要，隐藏密钥与秘密配置。
- **恢复：**崩溃/强制停止后显示持久化点、已完成动作、未完成动作和副作用未知项。只自动恢复草稿/阅读状态，不自动重放可能写文件、提交、推送或支付的工具；继续任务前核对现实状态。外部进程是否仍运行要单独检测。
- **验收：**在真实写文件和长命令途中强制退出，重启后结果仍可检查，已执行动作不被重复执行。未知结果保守标注；旧版会话可读取，记录和当前工作树变化不被混成同一次执行。

<a id="reverie-cli-feature-additions-2026-09-30--s17--可编辑计划与轻量目标r3"></a>

#### S17 — 可编辑计划与轻量目标（R3）

**决定：简化后新增。**复用已有任务条与工具任务列表，补目标/完成条件/步骤的用户控制；不默认引入无限自主运行。

- **行为：**用户可将任务固定为目标，写明完成条件、步骤和验证命令；计划可检查、编辑、增删/重排步骤。模型对计划的更新标明来源；目标编辑形成可追溯更新并在当前运行的安全点接收。
- **UI/UX：**输入器上方紧凑目标/步骤摘要，“运行”面板展开完整计划。完成步骤、待验证、受阻、暂停各有说明；不靠模型说“完成”就把整项目标自动标绿。
- **暂停/继续：**暂停在受控工具边界生效；尚在执行不能安全暂停的命令时显示“等待暂停”。停止命令走 S05。继续显示恢复摘要，不掩盖环境已变化。撤下目标与删除会话是不同动作。
- **取舍：**默认只做轻量目标和计划；硬时间/token/费用预算、无限自动续跑与复杂 Goal 调度暂缓为 X08。未取得真实用量时不给虚构百分比或成本。
- **验收：**编辑目标/完成条件、运行真实多步骤任务、工具边界暂停与继续，重启后计划恢复。未完成验证不能被系统自动标为验证通过；改目标不会杀掉核心或丢失正在输入的下一条消息。

<a id="reverie-cli-feature-additions-2026-09-30--s18--完成失败与待处理通知r3"></a>

#### S18 — 完成、失败与待处理通知（R3）

**决定：完善通知。**先解决本机长任务结果和审批可见性，不需要定时调度器。

- **事件：**完成、失败、需审批、恢复需核对进入应用内列表；每条关联项目/会话/运行/具体结果。后台窗口按系统支持情况发送通知；相同事件去重，持续运行无新结果不反复提示。
- **UI/UX：**入口紧凑显示未处理数量，列表可按项目过滤、查看/标已读；点击准确定位消息、日志或审批。静音和系统通知权限状态可查看；不会因静音停止任务。
- **边界：**系统通知被禁用时保留应用内状态；目标已归档、删除、路径失效时有明确降级。用户未请求的自动外部消息发送不进入本功能。
- **验收：**应用在后台完成/失败/需审批时收到正确本机通知；回跳不切错项目、不清草稿、不重复执行。静音后任务运行和未处理列表保持正确；系统不允许通知时不会报告已送达。

<a id="reverie-cli-feature-additions-2026-09-30--s19--本地独立工作目录生命周期r4"></a>

#### S19 — 本地独立工作目录生命周期（R4）

**决定：新增，与 S20 配套。**本机 worktree 能隔离文件，是 Reverie 编码产品值得增加的能力；不涉及云环境。[官方 Worktrees 参照](https://learn.chatgpt.com/docs/environments/git-worktrees)

- **创建：**在新会话或项目菜单选择“独立工作目录”，检查起始 branch/commit、实际目标路径及初始化 action；管理目录位于当前项目的本机管理区域并排除索引/版本误收集。默认从选定提交创建，不自动搬走当前未提交改动或复制秘密。选择包含改动时先展示明确文件范围，再执行可验证复制。
- **归属与 UI/UX：**创建对话框提供起始分支搜索、目标路径、未提交内容是否包含及初始化 action 摘要；取消和创建失败后保留用户选择。会话绑定工作目录，顶部和 Git 栏显示其真实路径/分支/起始提交。已有目录可打开系统编辑器、运行 action、创建分支、检查差异；归档/恢复表单显示保存范围与实际目录，不加入含混的 Local/Cloud 开关。
- **生命周期：**创建显示 Git/初始化实际阶段及失败恢复。归档前停止/处理相关运行与终端，检查未提交、未推送、非忽略未跟踪和需要保留的忽略文件；保存可恢复快照后才移除管理目录。用户指定永久目录不能自动清理。恢复还原快照并明确当前 HEAD/分支状态。
- **范围校验：**任何删除/移动均核对绝对目标、归属和允许的管理目录。被其他任务使用、含嵌套库/子模块或无法完整保存时给出原因并保留目录；禁止强制移除脏工作树。忽略文件不是天然可丢弃文件，用户需能决定哪些依赖/产物留存。
- **验收：**真实仓库创建两个独立工作目录，分别编辑不同分支并运行测试，原 checkout 不被修改。完成提交/普通推送后可回看成果；归档并恢复含未提交与未推送内容的目录，重要文件和提交一致。失败不会误删项目或其他 worktree。

<a id="reverie-cli-feature-additions-2026-09-30--s20--每会话执行器与并行写入协调r4"></a>

#### S20 — 每会话执行器与并行写入协调（R4）

**决定：新增真实隔离。**使用既有打包 Python 内核/bridge 的独立实例或经验证的等价隔离方式，不新增替代性的 UI Runtime。

- **执行：**每个活动会话有独立上下文、运行与停止生命周期；事件、输出、审批、附件和恢复记录绑定明确身份。当前会话切换不打断后台工作；启动数量有明确上限，超过时排队并说明原因。
- **写入：**应用启动的写任务按实际 checkout 协调；不同 worktree 可并行，同一工作目录的写任务排队，说明由哪个任务占用。只读任务是否并行由能力与上下文隔离决定。外部编辑器不受应用锁控制，仍需版本检查，不能宣称阻止了所有外部写入。
- **UI/UX：**侧栏显示每项运行/排队/需审批；全局运行列表可找到后台任务；停止 A 不停止 B。打开后台结果能回到准确工作目录；多条审批显示所属任务、目录和动作，避免误批。
- **兼容：**现有 managed SubAgents/RATS 与新会话执行器遵循资源上限和归属，不把子代理数量误算成独立会话数；共享配置更新和项目索引不能替换别的活动实例工作区。
- **验收：**打包版两个真实核心实例在不同 worktree 同时运行，分别产生可核对文件/日志，PID、事件与审批互不混用；停止其中一个，另一个继续成功。同 checkout 双写被应用排队；进程崩溃只影响所属任务并能保守恢复。模拟双标签不算并行证据。

<a id="reverie-cli-feature-additions-2026-09-30--s21--当前生效技能插件与连接状态r3"></a>

#### S21 — 当前生效技能、插件与连接状态（R3）

**决定：完善现有扩展页，保留 Reverie 特有能力。**不以新增连接市场为前提。

- **状态：**区分已安装、已启用、已信任、已授权、可调用及本项目/会话生效范围；显示缺依赖、授权失效、版本/来源和失败原因。已安装插件不等于连接账号已授权；模型知道 URL 不等于拥有访问权限。
- **UI/UX：**从输入器上下文/技能芯片或既有插件、技能、RATS 页面打开。以当前会话的有效能力摘要为先，底层工具/权限详情按需展开；冲突或禁用项给操作路径，不能只堆 manifest。凭据只显示来源/状态及撤销入口，不泄露值。
- **取舍：**先接现有连接与 MCP/插件报告的真实授权信息；没有授权协议的服务显示“不支持/未连接”。GitHub/GitLab PR 专项鉴权与统一账号连接器是 T01，不在这一项另造一个 OAuth 平台。
- **验收：**真实启用/禁用一个本地技能和插件、制造缺依赖/未授权状态，当前会话摘要与内核可调用工具一致。切项目后作用域正确，旧技能仍有兼容显示；撤销连接后相关调用实际不可用，而不是仅改变图标。

#### 8.2 工程与实际运行验证

1. 开始时读取适用的 AGENTS.md（如有）、工作区状态和相关实现，确认本文基线仍成立；已经完成的能力直接验证和复用。保存与当前任务无关的未提交改动，不清理整个工作区、不结束用户进程。
2. 对文件系统/Git/协议/进程生命周期增加有实际意义的聚焦测试；纯文案/间距不新增镜像实现的低价值测试。运行相关 Python 测试；桌面执行 `npm run typecheck`、`npm test`。
3. 软件阶段完成后在 `ReverieCli-ui` 执行 `npm run pack`，确认打包内核与 renderer 同步。需要可分发安装包时执行 `npm run dist:win`。运行实际输出的 `release/win-unpacked/ReverieUI.exe`，不能只启动开发服务器。

6. 只清理自己创建且已核对范围的临时文件/进程；清理被策略拒绝时记录实际位置和结果，不越过拒绝。自动快照或删除逻辑仍需逐项校验，不让测试清理触及工作区源文件。

<a id="rats-provider-generalization-handoff--required-target-design"></a>

### Required target design

<a id="rats-provider-generalization-handoff--1-provider-registry"></a>

#### 1. Provider registry

Replace ad hoc Engine assumptions with a small typed provider specification,
for example a Python dataclass or equivalent immutable record containing:

- `provider_id`;
- expected product identity;
- allowed service kinds;
- discovery-layout strategy;
- executable validation policy;
- supported permission classes or capability constraints;
- user-facing product label.

The production registry must still contain exactly one entry:

```text
reverie.engine / Reverie Engine / builtin
```

The registry must make a future second allowlisted provider an additive entry,
not require copying or renaming Engine-specific runtime logic.

<a id="rats-provider-generalization-handoff--2-provider-neutral-settings"></a>

#### 2. Provider-neutral settings

Introduce a versioned settings shape using provider-neutral names, such as
`enabledProviders` or `selections`, with at least:

- stable `providerId`;
- executable path;
- requested permissions;
- any provider-specific discovery-root identity required for reconnection.

Implement a deterministic migration from the current `enabledEngines` shape.
Existing users must not lose their saved Engine executable or permissions.
Write migration tests and ensure settings remain executable-local under
`.reverie/rats`.

Do not silently accept unknown provider IDs. Preserve the explicit production
registry and diagnostic reason for unsupported providers.

<a id="rats-provider-generalization-handoff--3-provider-neutral-runtimeapi-names"></a>

#### 3. Provider-neutral runtime/API names

Generalize new internal APIs and state fields toward names such as:

- `register_provider_executable()`;
- `set_provider_enabled()`;
- `RatsProviderSelection`;
- `enabledProviders`;
- `native_tool_name`;
- `ratsRegisterProvider`.

If compatibility aliases are needed for the existing desktop/core protocol,
keep them as a narrow migration layer with tests and a removal note. Do not
maintain two independent implementations.

Stable on-disk data and desktop-to-core protocol changes need an explicit
schema/version or compatibility strategy. Avoid a flag-day migration that
breaks packaged clients.

<a id="rats-provider-generalization-handoff--4-provider-neutral-tool-exposure"></a>

#### 4. Provider-neutral tool exposure

- Generate model-facing qualified names from `provider_id`, service ID, and
  native tool name without Engine-only constants.
- Prevent collisions when two providers expose the same native tool name.
- Make catalog descriptions and tags say RATS provider/native tool by default.
- Provider-specific metadata may add `reverie-engine` tags for the Engine entry,
  but the base wrapper must not do so unconditionally.
- Continue progressive definition loading; do not inject every schema into the
  system prompt.
- Keep tools with missing request schemas visible in the compact catalog but
  unavailable as direct model functions.

<a id="rats-provider-generalization-handoff--5-desktop-active-provider-selector"></a>

#### 5. Desktop active-provider selector

Update the RATS page so the product model is clear even while only one provider
exists:

- page introduction: RATS supports explicitly approved Reverie/Rilance
  providers;
- availability note: currently only Reverie Engine is implemented and appears
  in the selectable list;
- use generic labels such as `Register provider application`, `Provider
  executable`, `Saved but offline`, and `Supported provider` where appropriate;
- keep the displayed provider product and provider ID from live descriptor/
  handshake data;
- retain explicit enable and permission controls;
- retain the diagnostic drawer and rejection reasons;
- do not display placeholder cards or download buttons for products that do not
  exist.

The file picker may initially recognize only Reverie Engine because it is the
only registered product, but that specialization should live in the provider
registry/adapter rather than define the whole RATS UI model.

<a id="rats-provider-generalization-handoff--6-tests-proving-extensibility-without-fictional-production-support"></a>

#### 6. Tests proving extensibility without fictional production support

Add a test-only second provider specification through dependency injection or a
temporary registry fixture. Do not place it in the production allowlist.

Tests should prove:

- the production registry contains only `reverie.engine`;
- RATS itself is not hard-coded to one provider;
- settings migrate from `enabledEngines` without data loss;
- two injected allowlisted providers can coexist without selection, session,
  catalog, tool-name, or diagnostic collisions;
- an unknown provider remains rejected immediately;
- descriptor root and live identity validation use the selected provider spec;
- offline entries do not appear as live services;
- explicit enablement is still required;
- tokens and arguments remain absent from persisted/UI/log state;
- Engine-focused behavior and the real Engine RTP E2E remain unchanged.
