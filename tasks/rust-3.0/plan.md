## 二、Rust 架构、完整功能迁移与 Context Engine

### 2.1 工作区的六个主要职责

采用 Rust 1.96.0、Edition 2024，冻结工具链和依赖，使用锁文件构建。按六个主要职责组织工作区，扩展管理、授权和调度共用内核能力。

| 职责 | 完整范围 |
|---|---|
| 协议 | 内核握手、SDK actions、请求 ID、流式事件、错误、取消、用户询问、能力声明、插件和平台接口类型 |
| 内核 | Provider、模型、Agent、模式、工具、权限、会话、记忆、任务、扩展、授权及资源生命周期 |
| Context Engine | 扫描、解析、符号、引用、依赖、历史、文档/小说/资源索引、基础检索、语义推理、融合、重排和上下文预算 |
| 平台能力 | 文件、进程、命令、浏览器、Computer Use、多模态资源、系统凭据及平台适配 |
| 终端 | 滚动对话、输入编辑、流式输出、命令、询问、审批、管理面板及终端状态恢复 |
| 游戏运行时 | 场景、预制体、游戏逻辑、渲染、输入、音频、动画、UI、存档、验证和独立导出 |

Electron 连接支持多会话的常驻 Rust 内核，终端直接调用同一内核库。项目索引、Provider 客户端和后台资源在明确归属下共享；会话模型、规则、任务和权限保持独立。

网络请求、工具、索引、模型推理及后台任务统一处理取消、错误和正常关闭。取消必须区分尚未执行、已执行和交付不确定的操作，保留既有恢复与权限语义。

### 2.4 Context Engine 的完整实施结构

**结构索引：**

- 增量扫描、忽略规则、文件变化和工作区身份。
- Tree-sitter 解析、符号、引用、依赖及位置。
- Git 变更与历史。
- 配置、文档、小说和游戏资源。
- 正式基线支持的语言和文件类型。
- 解析失败、超大文件、重命名、删除、缓存修订及重启恢复。

**基础检索：**

- 精确标识符、符号、路径、锚点和词法检索。
- 排序、过滤、去重和证据定位。
- 依赖扩展、历史、长期记忆及指令发现。
- 上下文预算、压缩、片段选择和缓存失效。
- 查询到上下文组装的完整链路。

**语义增强：**

- 真实向量索引和近邻召回。
- 词法、结构与向量结果的混合融合。
- 有限候选神经重排。
- 中英跨语言、无精确标识符和跨文件难例。
- 统一返回路径、位置、内容版本和来源证据。

**一致性与生命周期：**

- 项目共用索引和修订管理，保护竞争写入。
- 基础索引及时更新，语义索引按修订追赶。
- 查询验证内容版本，准确展示更新进度和可用范围。
- 新一代索引完整建立后切换，失败保护上一可用状态。
- 关闭与取消释放模型、数据库、线程及进程资源。

### 2.5 本地语义资源

默认组合为：

- `multilingual-e5-small`，384 维。
- `bge-reranker-base`。
- Rust/FastEmbed/ONNX 本地推理。

语义向量化与神经重排全部本地运行。CPU 为基线，GPU 为可选加速；GPU 初始化或执行失败时明确报告并回退 CPU。

资源包独立发行，支持：

- 显式安装、离线导入、校验、更新和卸载。
- 原模型修订、模型/tokenizer 哈希、量化工具、许可证和运行时要求。
- Windows x64、Linux x64、macOS arm64/x64 CPU 推理。
- 模型及索引按需加载、首次预热和后台索引进度。
- 缺资源、损坏资源、更新中断、模型变化与索引重建。
- 默认通用 INT8 方案及量化前后质量对照。

通用 INT8 和四平台加载仍需真实验证。不能将仅针对 AVX-512 的资源当作 AMD 与 ARM 通用基线，也不能把资源下载成功当作查询能力验收。

### 2.6 Gamer 与 Live2D 的完整组件内容

Gamer 保留普通完整 2D、2.5D 游戏和 3D 小游戏范围，使用成熟 Rust 游戏库。保留现有场景、预制体、项目和数据格式，补齐需求到独立导出的制作闭环。

采用 Bevy 0.19.0，并通过 `bevy_rapier2d/3d 0.36.0` 锁定兼容物理依赖。适配器依赖的底层 `0.35.0-glamx0.2` 与底层 Rapier 0.36.0 分别记录。

游戏运行时为独立、按需启动的 Rust 组件，覆盖渲染、输入、音频、动画、UI、物理、存档、运行验证和打包。

| 完整作品 | 必需内容 |
|---|---|
| 2D 平台游戏 | 关卡推进、碰撞、失败/重试、完成状态、菜单、音效及存档 |
| 2.5D 探索游戏 | 场景、探索目标、交互、进度、完成状态、菜单及存档 |
| 3D 竞技小游戏 | 控制、战斗、敌人/回合、胜负、音效、设置及进度 |
| Galgame | 分支、结局、角色演出、回看、快进、设置及存读档 |

四个作品各约 10–30 分钟，能够从开始运行到结局，并在具备必要依赖的目标系统独立运行。Galgame 本身必须完整，Live2D 是可选演出组件。

重新核对现有 23 个类型和三种维度，冻结完整适用矩阵。适用组合必须有配置、系统、运行和导出证据，不能在验收失败后改为不适用。

3A 路线保留为后续决策：Unity/UE MCP＋Skills，或 Reverie Engine＋RAT/RATS＋Skills 插件路线。本次不实施该路线。

**Live2D 独立官方插件：**

- 插件可选安装，安装后的渲染必须使用原生 Cubism。
- Rust 控制入口负责配置、资源检查和工具调用。
- 通过版本化 C ABI 对接运行时，使用明确数据和句柄。
- 附带经许可核实的最小 Cubism Native 运行库。
- 下载入口显示“下载即同意”及条款链接。
- 真实验证 `.model3.json` / `.moc3`、绘制、遮罩、动作、表情、物理、视线和口型。
- 导出只包含必要运行库、资产和许可声明。
- 官方样例只用于许可允许的测试，默认不随插件或作品分发；占位模型不能通过验收。
- 先开发与测试，正式分发等待适用许可。下载同意不能替代发布授权。

适配通用 Agent Skills、Claude/Codex 插件布局、Agent Plugins 格式、Reverie 插件和标准 MCP 配置，完整覆盖 Skills、MCP、命令、子代理、Hooks、LSP 和配置。

平台专属 App 引用按实际依赖显示状态。存在公开 MCP 的服务进入 Reverie 授权流程，不能推断公开接口具备平台私有能力。

同来源重复安装去重，名称冲突使用可检查的命名空间。模型、工具、权限和配置映射必须可检查，未解析配置显示待配置。

外部运行时及缓存由管理器管理，避免重复部署。应用级安装与项目级启用、配置分别记录。

### 3.3 信任与 Connector 授权

- 信任由用户显式授予，主要到插件级；官方身份只作来源标识。
- 受信任扩展默认自动更新。
- 信任并启用后注册插件命令。
- Hooks 默认关闭，首次启用展示事件、入口和权限并明确确认。
- 来源、执行能力、权限、连接目标、依赖或条款变化暂停确认。
- 安装、启用、信任、授权和健康状态分别呈现。

Connector 首版采用公开 MCP＋OAuth，覆盖标准服务发现、PKCE、适用客户端注册、刷新、恢复、重新授权、撤销和 API Key。

凭据使用系统安全存储，不进入日志和模型上下文。MCP 的工具、资源/模板、提示词和客户端能力按实际实现声明，并兼容已有传输与配置。

真实授权验收包含授权、工具调用、刷新、恢复和撤销；模拟 token 不能替代真实服务验证。

### 3.4 扩展更新的完整校验要求

| 校验项 | 内容 |
|---|---|
| 来源身份 | 对应已安装来源及插件，固定提交/发行修订；发布者、来源或信任密钥变化需确认 |
| 内容完整性 | 对照可信清单的 SHA-256、大小及资产身份；Git 内容对应固定提交；安装后及切换前复核 |
| 数字签名 | 验证内容绑定和可信密钥；无效签名拒绝，来源要求验签时不降级 |
| 清单与组件 | schema、身份、版本、入口、必需文件、名称及统一注册映射 |
| 兼容性 | 内核/组件协议、系统、架构、运行时、ABI；模型资源另查维度、tokenizer 和推理接口 |
| 权限与配置变化 | 新执行能力、Hooks、权限、目标、依赖及条款；不能扩大原批准范围 |
| 安装路径 | 绝对路径、穿越、越界链接/reparse point、重名覆盖及入口范围 |
| 依赖与许可 | 版本、取得方式、安装动作及许可材料；新增依赖和脚本先确认 |
| 运行健康 | 受控解析、启动、握手、必需注册和配置加载；不执行业务 Hooks/命令或发起新授权 |

现有目录变化检测“signature”不能作为发布者数字签名。

缺少发布哈希、可验证签名且无法按固定 Git 内容验证的更新，保留候选，不自动启用或运行入口。用户批准具体候选哈希后，才继续验证。

哈希错误、无效签名、身份不符、损坏、越界或明确不兼容直接拒绝。对缺依据候选的批准不能绕过这些失败。

**原子切换：**

1. 下载、解包和校验在独立版本目录完成。
2. 切换前复核当前版本、信任、启用状态及批准范围。
3. 原子提交单一激活记录，绑定版本、内容身份和受管注册。
4. 已运行任务固定旧版本；独占组件等待旧任务结束，不强制终止。
5. 新版必需健康失败时恢复上一可用激活及注册。
6. 保留上一可用版和仍被任务引用的版本。
7. 重启恢复一致状态，避免混合新旧文件。

原子保证针对安装及激活状态。业务数据迁移另走一致性备份；不能证明回退兼容时暂停自动更新并确认恢复方案。

验收覆盖篡改、截断、缺依据、无效签名、来源替换、错误平台/协议、危险路径、新权限/依赖、健康失败、并发、中断、重启和 Windows 文件占用。

主基线使用重发并验收的纯 Python 2.5.5。原混合版保留对照，不能混用两版数据。

- 固定语言、文件、符号、过滤、结果数、位置、上下文预算和持久化。
- 启动计时到界面及必要内核连接可用。
- 结构索引计时到约定索引及持久化完成。
- 基础检索计时到结果及上下文组装完成。
- 必要工作不能通过延后执行退出计时。

分解启动、扫描、解析、序列化、IPC 等待与传输、排序、上下文组装、数据库及快照成本。正式包未插桩 wall time 判定门槛，追踪只作归因，记录开销、重叠和关键路径。

| 阶段 | 当前可达性判断 |
|---|---|
| 启动 | Python 引导及重复初始化有改善空间；Electron 和原生库固定成本须测量 |
| 扫描 | Rust 编排可能改善 Python 路径，文件系统成本仍形成下界 |
| 解析与图更新 | 数据组织、复制和图操作有空间，原生解析本身不能假定减半 |
| 序列化与 IPC | 内核和索引同进程可减少边界成本，Electron 桥接仍保留 |
| 排序与融合 | SQLite 和原生检索成本需实测，不能仅凭语言转换承诺 |
| 上下文组装 | 预算、依赖扩展、去重和复制可能改善，尚未验证 |

这些是推断。最终纯 Python 基线尚未产生，当前没有足够证据确定各阶段占比及减半可达性。

阶段 0 给出原始样本和 Amdahl 下界。保留成本超过整体 50% 时，仅优化其他部分无法使整体减半。

**启动、完整结构索引、基础检索的中位数与 p95 均须≤主基线的 50%。** 诊断小段不另设减半门槛。整体不可达时保持未通过，提出明确定义的替代口径由你决定。

### 4.3 质量、语义延迟与轻量门槛

轻量三项不得退于最终纯 Python 2.5.5：

| 指标 | 口径 |

### 5.3 CI 与候选资产

开发分支执行：

- Rust 锁定依赖构建、测试、格式检查、Clippy 及依赖/许可检查。
- 协议和前端类型生成一致性检查。
- 前端测试、类型、翻译及 renderer/Electron 构建。
- Context Engine 语料、质量和一致性验证。
- 平台能力和实际包检查。
- 官方插件、语义资源和 Gamer 的独立构建验证。

第一方验证与构建工具转为 Rust、Node 或 shell。第三方资源生产工具链单独管理，不成为第一方客户端的 Python 运行依赖。

候选资产包含来源 SHA、运行身份、系统、架构和大小。开发分支不得更新 `latest`、`plugins-latest`、正式标签或 Release。

### 5.4 发布守卫与事件矩阵

| 事件 | 发布行为 |
|---|---|
| `codex/rust-3.0` push | 测试、构建和 CI artifacts |
| PR | 只读验证及候选资产 |
| 开发分支手动运行 | 即使输入发布参数也禁止发布 |
| Rust main push | 核心门槛通过后按已确认政策更新 rolling latest |
| main 手动发布 | 通过同一来源和资产门槛后发布 |
| 合规版本标签 | 标签、版本、来源及构建门槛对应后生成稳定版草稿；最终实际资产及 DPI 验证后公开 |
| 非法标签 | 禁止发布 |
| Python 归档分支 | 不得影响主线发行资产 |

发布 job 自身限制 `main` 或合规版本标签，写权限集中于发布 job。当前手动发布缺少明确分支限制的问题必须修正。

### 5.5 正式 3.0.0 资产与完成状态

保留四平台 CLI 和桌面发行格式：

- Windows x64：CLI、安装包、便携包。
- Linux x64：CLI、AppImage、deb。
- macOS arm64/x64：CLI、桌面 DMG。
- 独立语义资源、官方插件和 Gamer 组件资产。

发布核对来源提交、版本、标签、架构、大小、SHA-256、内核记录、依赖资源和许可材料。实际包验收后不得悄悄更换未验证资产。

状态分别记录：

- 规划完成。
- 第一方功能实现。
- 实际构建与运行通过。
- 性能和质量通过。
- 3.0 核心正式发布。
- Gamer/Live2D 独立组件完成。
- 整个 3.0.0 完整产品验收完成。

正式纯 Python 基线、阶段占比、Recall 上限、量化质量、四平台推理、原生库和 Live2D 许可属于待取得证据。发现目标不可达、接口无法保持或许可不允许时，给出具体证据和备选方案由你决定，实施者不得自行缩小范围或降低门槛。
