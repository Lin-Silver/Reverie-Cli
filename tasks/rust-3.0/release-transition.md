## 原版保全

原版保全包含原提交、源码树、注释标签对象、完整 Release 响应、17 项实际资产和已有验收证据。每个资产固定 ID、名称、大小和 GitHub digest，并对保存的实际字节计算 SHA-256；只保存清单不足以代替完整资产备份。

源码 ZIP 同时核对归档中的提交注释、完整 CRC 和 SHA-256。原注释标签的完整内容按 Git 对象算法复核，保存的内容应重新计算出同一个标签对象 ID。

历史引用采用 `history/python-2.5.5-mixed-f029496`，指向原注释标签对象本身。该名称不匹配版本发布的 `v*` 标签规则；创建前还须核对当前全部 workflow 的事件和发布守卫。若本地或远端已有同名不同对象，停止并报告冲突，不覆盖。

保全及历史引用核对完成后，才能变更原正式标签或 Release。新的标签、源码和资产并无跨 Git/GitHub 接口的原子事务，必须保存逐步操作结果。

## 正式转换次序

| 次序 | 操作 | 必须回读核对 |
|---|---|---|
| 1 | 完成 Python 兼容候选的软件、四平台实包与旧索引备份恢复；保留未决规则供最终决定 | 来源 SHA、程序摘要、实际结果和未验证边界 |
| 2 | 检查原版保全及历史引用 | 原提交、原标签对象、17 项原资产大小与摘要 |
| 3 | 将原 Release 归档到历史引用，保留原 Release ID 与原资产 ID；保留原说明并补充历史身份说明 | 历史标签、名称、来源及全部原资产 ID/摘要仍一致 |
| 4 | 将已验收的最终候选直接推送 main | 远端 main 为最终候选；旧 main 是其祖先；没有混入其他会话改动 |
| 5 | 创建最终候选的 `v2.5.5` 注释标签，用原标签对象作为明确的更新保护条件 | 推送前旧对象仍为记录值；推送后新标签解引用到最终候选 |
| 6 | 版本标签 CI 四平台重新构建、执行原生验收并生成 17 项稳定草稿 | 全部作业、Test workflow、来源 SHA、草稿标志、资产集合 |
| 7 | 独立下载草稿中的最终程序与全部元数据，执行最终验收并处理未决规则 | 程序/内核记录/聚合记录/清单/checksums/GitHub digest 一致；实际 DPI 对应这些程序；合同决定已落实 |
| 8 | 本会话将验收通过的草稿公开 | `draft=false`，版本及来源正确，17 项实际公开资产与验收字节一致 |
| 9 | 建立最终纯 Python 归档与 Rust 开发工作区，冻结阶段 0B | `Reverie-Cli-py` 为完整项目快照；Rust 从同一最终来源开始 |

归档原 Release 的目的是保留原资产及其 ID，避免原混合版的文件被重发上传覆盖。原版与重发版分别使用独立 Release 身份，说明中公开两个来源及原版未验证项。历史资产的下载路径随历史引用改变，应在归档说明与重发说明中给出正确入口。

第 5 步使用针对单个标签的 `--force-with-lease=refs/tags/v2.5.5:<原标签对象>`。它不能替代操作前后的回读；远端对象若已变化，停止，不使用无条件强制覆盖。main 使用正常祖先推进，不强制更新。

第 6 步保持稳定 Release 为草稿且 `make_latest=false`。开发分支和 Python 归档分支不能创建 Release，也不能更新 `latest` 或 `plugins-latest`。

稳定草稿创建直接使用 REST 创建响应的不可变 ID；已有草稿先取得并校验 ID，再更新说明及来源。`target_commitish` 固定到验收提交 SHA。独立下载按已核实的 Release ID 读取草稿，不能把仅返回公开版本的 tag 查询当作草稿不存在，也不依赖创建后的即时列表传播。上传后核对全部 17 项的 ID、名称、大小、摘要和来源，保持草稿，等待实际程序及真实 DPI 验收。

来源 `84e3c92` 的实际 CI 上传成功后，草稿 ID `454761433` 的 `tag_name` 回读为 `untagged-…`，而源码标签仍正确指向该来源。原响应、完整发布日志和 17 项资产身份均已保全；显式 PATCH 标签、来源及草稿标志后，回读为 `v2.5.5`，同一 Release ID 与全部资产 ID、大小及摘要不变。没有公开发布。此前未保存创建及每一步修改的完整中间响应，不能据此断言字段变化的具体服务端原因。

工作流最终稳定草稿 PATCH 必须显式绑定标签及来源，再按不可变 ID 回读标签、来源、`draft=true`、`prerelease=false` 和 17 项资产数量；任何不匹配使发布作业失败。输出实际 Release ID 供独立核对。手工修正这一份草稿只能证明该次恢复，不能代替新工作流的真实 CI 验收；后续来源和标签推进仍按同一保全及 lease 次序进行，不重标旧程序或测试结果。

第 7 步若最终程序摘要与先前候选不同，先前 DPI 结果不能自动认证该程序；须验证最终程序。即便摘要相同，也须将原证据摘要与最终下载字节逐项绑定，并核对最终资产来源记录。源码运行、模拟坐标或字体缩放均不能替代真实 DPI。

## 中断与恢复

| 中断位置 | 保留状态与恢复要求 |
|---|---|
| 原资产保存不完整 | 原正式 Release、main 和正式标签保持原状；保留部分下载及失败记录，恢复校验 |
| 原 Release 归档后、候选公开前 | 原版仍在历史 Release；保持候选未公开，修复对应步骤并回读原资产 |
| main 或标签更新被并发变更拒绝 | 保存当前远端身份，核对变更来源，重新确定候选；不覆盖未知改动 |
| 构建、上传或最终资产验收失败 | 稳定草稿保持未公开；保留实际失败包、来源与日志，不套用其他包的结果 |
| DPI 失败或环境不可用 | 保持未通过/未验证，不豁免四档真实单屏验证，不开始 Rust 实施 |
| 公开后发现数据或发行错误 | 先保存问题程序及数据的一致性备份；按已验证兼容边界恢复，必要时将候选重新设为草稿并回读 |

二进制恢复与数据格式恢复分别处理。Python 派生索引可重建；原数据库、原文及配置必须保留。恢复演练使用副本和实际程序，不在用户工作区直接试验回滚。

公开操作前再次确认远端仓库、main、标签对象、草稿 ID、资产 ID/摘要和最后验收记录。尚缺环境或证据时报告最小缺失项，不将“候选构建成功”表述为纯 Python 重发或整个 Rust 3.0.0 完成。
